# v0.1.0-alpha.2 Release Notes

`v0.1.0-alpha.2` keeps the PostgreSQL extension SQL version at `0.1.0` and
changes the default retrieval experience to the latency-oriented fast path.

## Highlights

- `turbohybrid.profile` defaults to `latency`.
- Default candidate budgets are 100 dense candidates and 100 BM25 candidates.
- The default RRF constant is 60.
- `ORDER BY ... LIMIT n` is used as the final result target when possible.
- New indexes default to 4-bit quantization with `exact_storage = off`.
- BM25 latency paths are enabled by default for the latency profile, including
  WAND, eligible impact/head fast paths, hot postings cache, and documented
  approximate latency paths.
- Scan and index diagnostics expose the effective profile, budgets, final-k
  source, index use, phase timings, quantization, exact-storage state, and
  validation counters.

## Why It Changed

Earlier alpha builds required users to pass the recovered fast settings
explicitly. This release makes that setup the normal first experience: create a
standard `turbohybrid` index and run an `ORDER BY ... LIMIT n` query without
manually setting dense, BM25, or final-k budgets.

## Benchmark Snapshot

On the FIQA/OpenAI validation setup documented in
[FIQA/OpenAI Benchmark Snapshot](../benchmarks/fiqa-openai.md), the run used
57,638 corpus rows, 648 qrels-backed queries, 1,536-dimensional OpenAI
`text-embedding-3-small` embeddings, one warmup pass, one measured pass, the
`latency` profile, 4-bit quantization, `exact_storage = off`, and 100 dense plus
100 BM25 candidates. In that setup, `pgturbohybrid` default reported 0.910 ms
p95 and 0.421540 nDCG@10, compared with 3.254 ms p95 and 0.423341 nDCG@10 for
the SQL RRF hybrid baseline using pgvector HNSW default reloptions plus
PostgreSQL GIN FTS.

Results vary by dataset and hardware. See the benchmark page for the full table,
methodology, reproduction command shape, quality guard, and artifact policy.

## Migration Guidance

Earlier alpha users may see lower latency and a changed relevance/storage
tradeoff because the default profile is now latency-oriented and exact vector
storage is off by default.

Use a conservative profile when relevance safety matters more than the lowest
latency:

```sql
SET turbohybrid.profile = 'balanced';
```

Use the quality profile for final relevance-sensitive evaluation:

```sql
SET turbohybrid.profile = 'quality';
```

When exact vector rescoring matters, rebuild indexes with exact storage:

```sql
CREATE INDEX ... USING turbohybrid (...) WITH (exact_storage = on);
```

Explicit `dense_k`, `bm25_k`, `rrf_k`, and `final_k` query arguments continue
to override profile defaults.

## Risk Notes

- The extension is still alpha software.
- SQL APIs and the on-disk index format may change before a stable release.
- Relevance can vary by dataset; validate against qrels or a trusted SQL RRF
  baseline before relying on production settings.
- Parallel index build is disabled for the alpha access method until the dense
  graph and BM25 build paths have stronger parallel-build correctness evidence.
  `CREATE INDEX CONCURRENTLY` is covered by regression and restart tests.
- The extension depends on pgvector's SQL `vector` type and a compatibility copy
  of the vector varlena layout. pgvector ABI or layout drift may require a
  pgturbohybrid compatibility update.
